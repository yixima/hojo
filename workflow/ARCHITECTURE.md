# ワークフロー設計（第2版・2026-08-20 全面改訂）

## なぜ作り直したか

初版は**巡回先を人手で列挙**していた。これは原理的に漏れる。実際に起きた漏れ：

- 都道府県の産業振興外郭団体は47のうち**11しか把握できていなかった**
- 伝産協会の公告時期を「毎年4月上旬」と決めつけ、実際は年ごとに動いていた（2年分を取り逃す設計だった）
- 「7〜10月は端境期」としたが、JETROはその時期に翌年のジャパンパビリオンを公告していた
- JETROの設計・監理を候補に挙げたが、落札実績は166〜180万円で足切り基準未満だった

いずれも**「たぶん全部見た」という前提の甘さ**が原因。第2版は
**「何を母集団とし、そのうち何件を確認したか」を数えられる**構造にする。

## 層構造

```
[0] 母集団の確定    権威ある全国名簿から発注元を取り込む      harvest_orgs.py
        ↓
[1] 経路の発見      各組織の調達ページURLを自動特定           find_procurement.py
        ↓
[2] 横断の網        アグリゲータで[0]の漏れを拾う             （調達ポータル / jGrants / 各電子調達）
        ↓
[3] 収集            各経路から案件を抽出                      sweep.py
        ↓
[4] 判定            足切り・応募形態・格付                    eligibility.md
        ↓
[5] 金額            予定価格が非公開でも規模を推定            下記「金額の決め方」
        ↓
[6] 成果物          レポート／案件リスト／Excel               make_case_list.py, check_links.py
        ↓
[7] 検証            網羅率と再現率を数える                    coverage / known_positives
```

## [0] 母集団の確定

**行政が公表している全国名簿を起点にする。** 名簿がある限り「列挙漏れ」は名簿側の
問題として切り分けられる。人手の記憶に依存しない。

| ID | 名簿 | 母集団 |
|---|---|---|
| `chusho_shien` | 中小企業庁「都道府県等中小企業支援センター等」 | 47都道府県＋政令市の支援センター |
| `clair_rliea` | CLAIR「地域国際化協会一覧」 | 総務省認定の中核的民間国際交流組織 |
| `jnet21` | J-Net21「中小企業支援を行う公的機関一覧」 | 上記に入らない公的支援機関 |

```bash
python3 workflow/harvest_orgs.py
```

出力 `data/registry/orgs.csv`。**抽出件数が想定下限を割ったら警告を出す** ──
一覧ページの構造変更で黙って0件になるのが最悪のため。

### tier の付け方

**tier は「直接巡回する頻度」であって、「無視してよい系統」ではない。**
生島様のご指示（2026-08-20）:「全てが最優先で、優先順位を低くしても良いものは存在しない」。
tier が低い系統は**アグリゲータと全文検索で網をかける**。カバーしない系統は作らない。

| tier | 対象 | 直接巡回の頻度 | 低頻度でも漏らさない手段 |
|---|---|---|---|
| `tier_a` | 自治体本体（都道府県47・政令市20）、地方支分部局、中小企業支援センター、主戦場直結団体 | 毎週 | — |
| `tier_b` | 名称に伝統・工芸・文化・観光・貿易・デザイン等を持つ団体 | 毎週 | — |
| `tier_c` | 地域国際化協会 | 隔週 | 全文検索で補う |
| `tier_d` | その他の公的支援機関 | 月次 | 全文検索で補う |
| `tier_z` | 事業と明確に無関係（ナースセンター、信用保証協会等） | 直接巡回しない | **アグリゲータには載るので拾える** |

`tier_z` は「巡回コストを払わない」だけで、調達ポータル・GEPS・全文検索の網からは
外さない。**除外ではなく、経路を変えているだけ。**

**tier_a を「名称の語感」ではなく「実績のある類型」で決めている**のが要点。
東京都中小企業振興公社は名称に工芸も海外も入らないが、御社の最大の取引先である。

### 2026-08-20 に実際に起きた取りこぼしと、その構造

生島様から2件のご指摘を受けた。いずれも**系統ごと欠けていた**もので、
運用の不注意ではなく設計の穴だった。

| 漏れた案件 | 欠けていた系統 | なぜ気づけなかったか |
|---|---|---|
| 九州経済産業局の伝統工芸品・地産品 海外展開事業 | **中央省庁の地方支分部局** | `meti.go.jp` は登録済みだったので「経産省は見ている」と誤認していた。経済産業局は全国9局それぞれ別ドメイン・別調達ページ |
| 山形県庁の地産品 海外展開事業 | **自治体本体** | 山形県企業振興公社（外郭団体）は登録済みだった。**外郭団体だけを見て本体を見ていなかった** |

対策として `harvest_government.py` を新設し、都道府県47・政令市20・経済産業局9局を登録した。

**教訓**: ある系統の一部を登録すると「その系統は見ている」と錯覚する。
`meti.go.jp` があるから経産省系は網羅、`山形県企業振興公社` があるから山形は網羅 ──
どちらも誤り。**系統は「本体・地方支分部局・外郭団体」の3層で必ず揃える。**

### まだ取り込んでいない母集団（次にやること）

- 市区町村 1,700超（アグリゲータ[2]と全文検索で拾う方針）

## [1] 経路の発見

公的機関の調達ページURLに規則性は無い（`/nyusatsu/` `/keiyaku/` `/chotatsu/`
`/procurement/` `/koubo/` …）。171組織を人手で探すのは非現実的なので機械化する。

```bash
python3 workflow/find_procurement.py          # 未発見のものだけ
python3 workflow/find_procurement.py --all    # 全件やり直し
```

リンクのラベルとURLパスを採点し、**取得したページに実際に案件が載っているか**まで
確認する（`looks_like_listing`）。ナビだけの空ページを掴まないため。
見つからないものは `要手動確認` として残す。**黙って諦めない。**

## [3] 収集（sweep）

```bash
python3 workflow/sweep.py --tier tier_a        # 確認済みの調達ページを巡回
python3 workflow/sweep.py --min-score 0        # 落としたものも含め全部見る
```

出力 `data/sweep/sweep_YYYYMMDD.csv`。

**このスクリプトは判断しない。** 広く拾って関連度スコアを付けるだけ。
足切り・応募形態・格付・金額の判断は [4][5] で行い、その結果が
`data/cases/cases_YYYYMMDD.csv` になる。
**機械の仕事（再現性が要る）と判断の仕事（文脈が要る）を混ぜない。**
混ぜると「なぜ拾わなかったのか」が追えなくなる。

### 2つの抽出経路を必ず両方使う

| 経路 | 対象 |
|---|---|
| `extract_cases` | 案件名がリンクになっているページ（大半の自治体・協会） |
| `extract_table_cases` | **案件名が表のテキストで、リンクが無いページ** |

後者が要る理由：東京都中小企業振興公社の契約情報は件名が表のテキストで、
応募はビジネスチャンス・ナビ側で行うためリンクが無い。
リンクだけを見て **0件と誤検出した**。表抽出を足して 0件→41件 になった。

### 関連度スコア

`DOMAIN_WORDS` との一致で採点する。主戦場語（伝統工芸・海外展開・パビリオン等）は
重み2、隣接語（海外・展示会・観光等）は重み1。`OFF_DOMAIN`（清掃・警備・道路等）が
主題なら -1。

**スコア0でも捨てずに残す**（`--min-score 0` で全件見られる）。
捨てた記録が無いと、漏れたときに原因が追えない。

## [5] 金額の決め方

**予定価格が非公開でも金額欄を空にしない。** 空欄は「調べていない」と区別がつかない。
次の順に確度を落としながら必ず何かを書く。

| 優先 | 方法 | 金額確度 |
|---|---|---|
| 1 | 公募要領・公告に明記された補助上限額／委託限度額 | `◎確定` |
| 2 | **過年度の同一案件の落札金額**（`sources.yaml` の `award_amounts` 参照） | `◎確定（前年同案件の落札額）` |
| 3 | 類似案件の落札金額レンジ | `△推定（実績レンジ）` |
| 4 | **仕様書の内容からの積算** ← 1〜3が取れない場合 | `△推定（仕様書から積算）` |
| 5 | どれも不可 | `－非公開` ＋ 何を確認したかを根拠欄に書く |

### 4. 仕様書からの積算のやり方

過去の落札金額がどうしても見つからない場合はこれを使う。**必ず `△推定（仕様書から積算）`
と明記し、積算の内訳を「金額の根拠」列に書く。** 推定を確定と誤読させないため。

仕様書から拾う変数：

- 履行期間（月数）と想定投入人数 → 人件費
- 開催回数・会場規模・想定来場者数 → 会場費・運営費
- 対象国数・渡航回数・渡航人数 → 旅費（別添の旅費基準があればそれを使う）
- 出展小間数・小間単価 → 出展料・装飾費
- 制作物の点数と言語数 → 制作費・翻訳費
- 再委託の可否と上限割合

御社の実績を単価の基準に使う：**令和7年度「東京手仕事」MAISON & OBJET 出展及び
ポップアップストア運営 = 40,986,000円（税込）**。積算内訳書がDriveにあるので、
同種案件はこれを基準に規模比で按分する。

記載例：
```
△推定（仕様書から積算）
仕様書より 履行期間6か月・対象2都市・出展小間12・想定投入3名。
令和7年度 東京手仕事 MAISON&OBJET（40,986,000円／パリ1都市・6か月）を基準に
都市数と小間数で按分し、概ね5,000〜6,500万円と推定
```

## [7] 検証 ── ここが第2版の核心

「たぶん漏れていない」ではなく、**数える。**

### 網羅率

`data/registry/orgs.csv` の `status` を数える。
確認済み／要手動確認／到達不可／未確認 の内訳を毎回レポート末尾に出す。
**未確認が残っていることを隠さない。**

### 再現率（known positives）

`data/registry/known_positives.csv` に「本来必ず拾えるべき案件」を置く。
- 御社の過去の受注案件
- 生島様が既にご存じの案件
- 過去のレポートで拾えた案件

毎回、**現在のワークフローがそれらを拾えるかを検査する**。拾えなければ、
その案件を拾える経路をレジストリに追加する。**漏れを見つけたら仕組みを直す**という
ループを回すための仕掛け。

```bash
python3 workflow/check_recall.py
```
