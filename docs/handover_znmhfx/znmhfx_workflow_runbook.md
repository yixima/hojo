> **設計の全体像は `workflow/ARCHITECTURE.md` を先に読むこと。**
> 2026-08-20 に、巡回先を人手で列挙する方式から
> 「権威ある全国名簿を母集団とし、網羅率と再現率を数える」方式へ全面改訂した。

毎週1回、この手順を最初から最後まで実行する。

## 手順0：ネットワーク到達性の確認と、許可ドメインの育成

### 前提の確認（最初に必ず行う）

```bash
curl -sS -o /dev/null -w "%{http_code}\n" --max-time 15 https://www.jgrants-portal.go.jp/
```

`000` が返る場合、クラウド環境のネットワークアクセスが `Trusted` のままで、
公的機関のサイトが全て遮断されている。この状態では公募要領を読めないため、
**WebSearch だけで判定できる範囲に留め、レポート冒頭にその旨を明記する。**

解消するには、claude.ai/code の環境セレクタ（メッセージ入力欄の上の雲アイコン）から
ネットワークアクセスを `Custom` にし、`workflow/sources.yaml` の
`network_allowlist` を「許可されたドメイン」に登録する。
「一般的なパッケージマネージャーのデフォルトリストも含める」のチェックは必ずオンにする。

### 遮断に遭遇したら記録する（重要）

公的機関のドメインは統一されていない（`sources.yaml` の `domain_survey` を参照）。
許可リストは完璧にはならないので、**巡回中に `EGRESS_BLOCKED` に遭遇したら、
そのドメインを必ず記録し、レポート末尾の「追加すべき許可ドメイン」に列挙する。**

ドメインの存在確認はHTTPが通らなくてもDNSで可能：

```bash
getent hosts www.example.lg.jp && echo 実在 || echo 不明
```

この積み重ねで許可リストを育てる。放置すると、その発注機関の案件は永久に拾えない。

## 巡回密度の季節調整

この分野の公募には強い季節性がある（2026-08-19の初回巡回で確認）。

**【2026-08-20 全面改訂】** 初回に置いた「7〜10月は端境期」は、過年度の実測で
**誤りだった。** 発注元ごとに繁忙期が違う。一律の季節調整はしない。

| 時期 | 主に動く発注元 | 巡回の密度 |
|---|---|---|
| **3月中旬〜7月上旬** | **伝産協会**（海外テストマーケティング／実演・ワークショップ／英語翻訳） | **毎週。取り逃すと1年待ち** |
| **7月〜11月** | **JETRO**（翌年のジャパンパビリオン設計・監理を展示会ごとに公告） | **毎週。ここは端境期ではない** |
| **8月中旬** | 東京都中小企業振興公社（東京都伝統工芸品展 運営管理） | 毎週 |
| **2月〜3月** | 東京都中小企業振興公社（**東京手仕事 MAISON & OBJET 出展運営 ← 最重要**） | **毎週。最優先** |
| 5月中旬 | 東京都中小企業振興公社（TOKYO職人展 運営管理） | 毎週 |
| 12月〜3月 | 国の補助金（翌年度予算に基づく公募） | 毎週 |

要するに **tier_a は通年で毎週確認する。** 季節で手を抜ける時期は無い。

### 個別の注意

- **伝産協会の公告時期は年ごとに動く。** 令和6年度は2024-06-26公告、令和7年度は
  2025-06-23公告、令和8年度は2026-04-01公告。「4月だけ見る」と2年分を取り逃す。
  **3月中旬から7月上旬まで、緩めずに毎週見ること。**
- **東京手仕事 MAISON & OBJET は御社が令和7年度に受注した案件そのもの**で、
  3年連続で発注されている。令和7年度分の入札書は2025-03-18。
  **2027年1月から公社の契約情報を毎週確認すること。** ここが最大の再受注機会。
- 公社案件は**ビジネスチャンス・ナビ側の詳細ページにしかない情報がある**
  （契約方法、案件受付期間、入札資格の有無）。`workflow/fetch_chancenavi.py` で
  ログイン不要で取得できる。公社サイトの一覧だけで判断しない。

## 手順3：優先サイトの直接確認

`workflow/sources.yaml` の各 tier に `frequency` を設定してある。それに従う。

| frequency | 対象 | タイミング |
|---|---|---|
| `every_run` | **tier_a**（7組織） | **毎回必ず直接確認** |
| `monthly` | tier_b 府省庁、tier_c 国の外郭団体、tier_h 集約サイト | 月1回（第1週） |
| `seasonal` | tier_d 商工会議所、tier_e 都道府県外郭団体、tier_f 自治体、tier_g 観光・文化 | 12〜6月は毎週、7〜11月は月1回 |
| `websearch` | 市区町村、地方の商工会議所 | 直接巡回せず手順2で拾う |

### tier_a（毎回必ず確認する7組織）

1. **伝統的工芸品産業振興協会** — 主力事業と最も一致。4月上旬公告
2. **東京都中小企業振興公社** — 受注実績あり。`tokyoteshigoto.tokyo` も併せて確認
3. **自治体国際化協会（CLAIR）** — パリ等に海外事務所。新規開拓の本命
4. **JETRO** — 調達情報ページ
5. **中小機構** — JAPANブランド、TAKUMI NEXT
6. **中小企業庁** — 支援機関側で申請できる補助金
7. **国際交流基金（JF）**

### tier_e（都道府県の産業振興外郭団体）の扱い

**最も見落としやすい発注元。** 都道府県本体ではなく外郭団体が海外展示会出展事業の
運営委託を出す。御社の受注実績である東京都中小企業振興公社がこの類型。
47都道府県すべてに同種団体があるが、現時点で判明しているのは11団体のみ。

**毎回1〜2県ずつ調査して `sources.yaml` の `tier_e_prefectural_agencies.verified`
に追記すること。** 「◯◯県 中小企業振興公社 海外展示会 公募」で検索する。
これを続ければ1年以内に47県を網羅できる。

## 手順4：判定

見つかった各案件について、`workflow/eligibility.md` の手順を適用する。

1. 足切り判定（500万円未満・締切超過・除外語・地域限定・個人限定）
2. 応募形態の判定（単独／共同／支援側／受託）
3. 全省庁統一資格の要否と間に合うか
4. スコアリング（S/A/B/C）
5. 実績要件を満たせるか

**判定の根拠となる記述は、公募要領の該当箇所を引用して残すこと。**
「応募できます」だけでは生島様が確認できない。

### 締切の扱い

残日数は **直近アクション期限**（説明会申込・質問締切・資格申請期限など、締切より前に
来る公表期限）で測る。締切だけを見ると取り逃す。詳細は `workflow/case-list-schema.md`。

| 残日数 | 表示 |
|---|---|
| **7日以下** | **【至急】** 準備期間がほぼない。提出可否の即断が必要 |
| 8〜21日 | **【要着手】** 通常の提案書作成期間 |
| 22日以上 | 通常 |

## 手順5：台帳への追記

`data/ledger.csv` に追記する。列は以下。

```csv
初報日,案件名,発注機関,種別,締切,予定価格,格付,応募形態,資格要否,状態,URL
```

- `種別`: 補助金 / 企画競争 / 企画提案 / プロポーザル
- `応募形態`: 単独 / 共同 / 支援側 / 受託
- `資格要否`: 不要 / 要（間に合う）/ 要（間に合わない）
- `状態`: 新規 / 検討中 / 提出済 / 見送り / 締切超過（初報時は「新規」）

追記したらコミットしてプッシュする。

```bash
git add data/ledger.csv && git commit -m "週次巡回 YYYY-MM-DD" && git push
```

## 手順5.5：案件リストの作成（毎回必須）

レポートとは**別に**、その回に洗い出した案件の一覧を作る。仕様は
`workflow/case-list-schema.md`（22項目・一覧は9列）。

```bash
# その回のCSVを作る
$EDITOR data/cases/cases_$(date +%Y%m%d).csv
```

- 実体: `data/cases/cases_YYYYMMDD.csv`
- 表示: 同内容を一覧アーティファクトとして公開し、各行から**レポートの該当節へリンク**する
- `data/ledger.csv` との違い: 台帳は通期の履歴、案件リストはその回の棚卸し。
  台帳に既出でも、その回に判定が動いたもの・締切が迫っているものはリストに載せる
- 判定が `見送り` の案件も行を消さない。翌年度に同じ公募が出るため記録として残す

**チェック**: リストの緊急度・件数と、レポート本文の記述が食い違っていないか必ず突き合わせる。
リストは残日数を直近アクション期限で測るため、締切基準で書いたレポートとずれやすい。

### 予測案件も載せる（区分=予測）

いま公募中のものだけでなく、**過去の公告実績から近く出ると見込まれる案件**も
同じリストに `区分=予測` として載せる。申請候補のパイプラインを切らさないため。

予測は必ず**根拠つき**で書く。「例年出ている気がする」は載せない。
`予測の根拠` 列に「何年連続で、いつ公告されたか」を実測値で書くこと。
根拠は過年度の公告一覧から取る：

```bash
# 東京都中小企業振興公社 過年度契約情報
https://www.tokyo-kosha.or.jp/kosha/keiyaku/end/index.html
# 伝産協会 公募公告（ページ送りで全件辿れる）
https://kyokai.kougeihin.jp/association_cat/公募公告/page/N/
# JETRO 入札情報のカテゴリ別（設計監理・展示会の施工）
https://www.jetro.go.jp/procurement/bidtop/bid/service06/
```

**Excel を生成する。** CSV を UTF-8（BOMなし）で渡すと Mac の Excel で文字化けする。

```bash
python3 workflow/make_case_list.py data/cases/cases_YYYYMMDD.csv
```

これで `.xlsx` が出力され、CSV も BOM 付きに書き直される。

**リンクを検証する。**

```bash
python3 workflow/check_links.py data/cases/cases_YYYYMMDD.csv
```

`FAIL 0` になるまで配布しない。**HTTP 200 だけでは不十分**で、POST専用ページは
200 を返しながら中身が空になる（ビジネスチャンス・ナビの案件詳細が実例）。
詳細は `workflow/case-list-schema.md` の「リンクの検証」を参照。
