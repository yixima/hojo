## 1. 何が起きたか

ユーザー（生島様）への定期報告は、`send_later`（1回だけ発火する予約）を
**「今回の報告の中で、次回の予約を1本入れる」**という形で繋いでいた。

実測した鎖（`list_triggers` で全件確認。すべて `ended_reason=run_once_fired`）：

| # | 発火日 | 次の予約を作ったか |
|---|---|---|
| 1〜6 | 9/1・9/4・9/5・9/7・9/8・9/8 | 作った |
| 7 | **9/9 10:04** | **作らなかった** |

7本目に応答したあと、私は次の環を作らなかった。
**鎖はそこで終わり、以後いかなる予約も存在しなかった。**

空白＝**2026-09-09 10:04 → 2026-09-11 15:44 ＝ 2日5時間40分。**
再開の合図になったのは、生島様の「定期巡回と報告が何日も止まっていました」という**ご指摘**である。
自力では検出していない。

なお、**週次巡回の Routine（`trig_01NgT5dQwMBGg8APfz8YSG9K`）は壊れていない。**
`0 6 * * 0`（日曜08:06 JST）で正常に生きており、次回は 2026-09-14 08:06 JST。
壊れたのは**日次の報告の鎖だけ**である（§3-15：原因を1つに丸めない）。

## 2. 被害

- 締切が動いている案件について、2日以上、判断材料が生島様の画面に届かなかった。
- 実際に危険だったことが、停止解除の直後に判明した。
  **本日 9/11 17:00 に3件が同時に閉じる**（GREEN×EXPO 2027 会場内学習プログラム／
  食品工場Week／九州機械要素技術展）。気づいた時点で**残り1時間16分**だった。
  9/9 に報告が続いていれば、2日間の検討時間があった。
- **この業務における報告の停止は、単なる遅延ではない。**
  締切管理の業務では、届かなかった報告は**案件を1件丸ごと失わせる**（本リポジトリ `CLAUDE.md` 冒頭）。

## 3. 直接原因

**単発予約（one-shot）の鎖には、自己修復も不在検知もない。**

```
報告 → 次回を予約 → 報告 → 次回を予約 → 報告 → （予約を忘れる） → 永久に無音
```

- 各環の生成は**私の手作業**であり、手作業は抜ける。
- 抜けても**エラーは出ない**。予約が「無い」ことは、誰も観測していないからである。
- 監視の言葉でいえば、**エラーの発生を見張っていて、沈黙を見張っていなかった。**

## 4. 拡大原因（なぜ2日も気づけなかったか）

### ① 沈黙は画面に出ない

生島様の画面には、公募ボード（Artifact）が**9/9 時点の内容のまま**表示され続けていた。
**古い情報は「古い」とは表示されない。**正しい情報と見分けがつかない。
「更新が止まっている」という事実を**成果物そのものが隠していた。**

### ② 同じ失敗を、私は既に文書化していた

別 Routine（Mac の監視）のプロンプトに、私はこう書いていた。

> 細かい確認（`send_later` の鎖）が主役で、これはその鎖が切れたときに拾うための保険である。
> この監視は一度、17時間半にわたり無言で停止した実績がある。

**同じ設計の弱点を、同じ言葉で、自分で書いていた。**
そちらには保険（毎時の定期実行）を付け、**こちらには付けなかった。**
知識としては持っていたが、**適用しなかった。**
§0-14 の言う通り、**足りないのは条項ではなく発動である。**

### ③ 「1応答＝1完了単位」（§2-20）を、報告の鎖に適用していなかった

§2-20 は「完了した単位は、その応答の中で永続化まで済ませる。次の応答に持ち越すと、そこで失われる」と定める。
**次回の予約は、まさに『次の応答に持ち越したら失われるもの』だった。**
私はこれを「報告のおまけ」と扱い、完了単位として扱っていなかった。

## 5. 再発防止（既存条項の発動経路の強化。新条項なし）

### 第1層：鎖をやめ、定期実行（cron）に置き換える

| | 単発予約の鎖 | 定期実行 |
|---|---|---|
| 1回抜けたら | **永久に止まる** | 翌日また発火する |
| 生成者 | 私（抜ける） | サーバ（抜けない） |

- 新設：`trig_013J6yq98fZPqmqdvcfdLmDs` ／ `0 23 * * *`（**毎日 08:00 JST**）／このセッションに結び付け。
- プロンプトに次を明記した。
  - `./bin/today.sh` → `build_board.py --check` → `heartbeat.py --check` →
    Artifact を `read` してから再公開 → `heartbeat.py --stamp` → push
  - **72時間以内に閉じる締切を全件書く**
  - 前回報告からの空白時間を書く
  - **「新規0件・変化なしでも必ず報告する。黙って終わらない」**
  - **自分自身の `enabled` と `next_run_at` を毎回確認する**（監視が死んだことを監視する）

### 第2層：不在検知（デッドマン装置）を成果物の上に置く

止まったことが、**見ている画面そのものに出る**ようにした。

- `bin/heartbeat.py`：`--stamp` で `data/heartbeat.json` に報告時刻を刻み、
  `--check` で空白が **36時間**を超えたら終了コード1。
- `bin/build_board.py` がこれを読み、**空白が閾値を超えていれば公募ボードの最上部に赤帯を出す。**
  「この画面の更新が途切れていました」と、**画面自身が名乗る。**

これが ④ の「古い情報は古いと表示されない」への直接の回答である。
**私が黙っても、成果物が黙らない。**

## 6. マニュアル側への提案（条文の追加ではなく、既存条項の適用範囲の拡張）

§0-14 に従い、**新条項は提案しない。**§2-18 の**適用範囲の拡張**を1点だけ提案する。

> **§2-18 への追記案（1文）**
> 応答をまたいで継続すべき業務を仕組みに預けるときは、**単発の予約を自分で繋ぐ方式を採らない。**
> 定期実行に預け、**前回実行からの空白時間を成果物の上に表示する**（不在検知）。

理由：§2-18 は現在「**そう言ってはいけない**」（実態のない「処理中です」の禁止）を定めているが、
**「ではどう作るか」を定めていない。**本件は、§2-18 を完全に理解したうえで、
その理解が**設計に届かなかった**事例である。禁止の条文に、**代替の設計を1行添える**ことで発動経路が閉じる。

これは v17 が採った方針（**新設0件・既存条項の適用範囲と発動経路の強化**）と同じ形である。
